# Variants — choosing a look by seeing it

For a choice that words do not settle: which of two hierarchies, how dense, how loud. Not for
a choice the project's tokens or `house.md` already made.

## What is built

The same piece, with the same content and the same data, in three versions on one page, and
a switch between them: three buttons, or the keys 1, 2, 3. Each version differs from the
others along one axis that has a name (density, hierarchy, tone), said above the switch, so
the choice is between ideas and not between accidents. Two axes at once make six versions
and no decision.

All three are built from the project's tokens and its components. A version that needs a
new colour or a new size is a proposal about the tokens and is said as one.

The switch lives where it cannot ship by mistake: one file or one route that nothing else
imports, named for what it is. Worst-case content in all three: the longest name, the empty
list, the number with six digits. A version that only works with tidy data loses there.

## After the choice

The chosen version moves to its place; the other two and the switch are deleted in the same
change, not left behind a flag. One line stays in the project's notes: what was chosen,
along which axis, and why. That line is what keeps the next screen from reopening it.

## Report

    VARIANTS  <piece>  axis: <name>
      1  <what it does along the axis>
      2  ...
      3  ...
    open: <path or route>   keys 1 2 3
    chosen: <n>, because <the user's reason>    removed: <files>

(Several versions side by side behind a switch: after emilkowalski/skills, MIT, `prototype`.
It is also how a look is designed without a canvas tool: the medium is the code.)
